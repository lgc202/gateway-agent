# 输入规范化与可靠执行实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: 使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 逐个 Task 执行本计划。所有步骤使用 `- [ ]` 跟踪，不允许跳过验证直接宣布完成。

> 状态：计划审查完成，等待实施
> 编写日期：2026-07-22

**目标：** 在当前可运行的 Chat/Message API 上，交付“用户消息可靠创建 Task/Run → Outbox 唤醒 Temporal → Worker 使用 Eino 规范化输入 → MySQL 保存最终 Assistant Message 与 Task Event → Redis Pub/Sub 提醒 Chat SSE”的完整闭环。

**架构：** MySQL 保存全部业务事实；apiserver 负责 HTTP、消息事务、Outbox Publisher 和 Chat SSE；worker 负责 Temporal Workflow/Activity、Run 状态推进和 Eino Normalizer。当前回复由确定性 Response Composer 一次写入 MySQL，Redis 只使用 Pub/Sub 做事件提醒，不实现 Streams 和模型回复流。

**技术栈：** Go 1.26、Gin 1.12、Google Wire 0.7、MySQL 8.4、sqlc 1.29、Temporal Go SDK 1.46.0、Eino 0.9.12、Eino OpenAI Adapter 0.1.13、go-redis 9.21.0、Viper 1.20、OpenAPI 3.1、Docker Compose。

## 0. 强制执行约束

这些约束适用于本计划的每一个 Task。

### 0.1 开发方式

- 直接在 `main` 工作，不创建分支或 worktree；这是用户已经确认的仓库工作方式。
- 每次只执行一个 Task。开始前说明为什么需要，结束后展示完整 Diff 和真实验证结果。
- 只在一个可编译、可运行的稳定点提交；提交必须聚焦，不把多个不相关能力塞进一个 commit。
- 不自动 push。

### 0.2 不写测试

- 不创建任何 `*_test.go`、Mock、Fake、测试专用接口或测试夹具。
- 从 `make verify` 删除 `go test ./...`，避免计划口头说“不写测试”但质量命令仍执行测试。
- 使用 `make generate`、`make verify-generated`、`go vet ./...`、`go build ./...`、Migration、真实 MySQL/Temporal/Redis、curl 和 SSE 连接验证。
- 外部模型验证必须连接真实的 OpenAI-compatible/Higress AI Gateway；没有凭证时明确报告外部阻塞，不能用假模型冒充完成。

### 0.3 编码规范

- 注释使用中文；Go 标识符、JSON 字段、事件名、错误码和配置键使用英文。
- Handler 只处理 HTTP/SSE 协议、输入绑定、参数校验、错误映射和响应输出。
- Service 承载用例、事务和业务语义；Store 只封装 sqlc、数据库和 Redis 访问。
- sqlc、Gin、Redis、Temporal 和 Eino 类型不得穿透到不属于它们的层。
- 不为单一实现提前定义接口；只使用 SDK 已提供的真实边界接口，或在消费者侧为多个生产实现定义小接口。
- 对 HTTP、配置、MySQL、Redis、Temporal Payload 和模型输出做严格校验；对包内刚构造、语义已确定的值不重复判空和层层防御。
- 主流程优先保持直接，不为了少写几行重复代码制造四五层 helper。
- 不创建 `bootstrap`、`core`、`platform`、`common`、`utils`、`apperror`。
- 技术扩展包使用 `x` 后缀；只有两个程序真实复用且能减少重复时才放入 `internal/pkg`。
- 不创建空目录、空 Service、空 Store、空接口、TODO 实现或只为未来保留的字段。

### 0.4 当前明确不实现

- OIDC 登录、Session、Group Mapping 和 RBAC；当前无鉴权模式只能监听 loopback，不能部署到企业网络。
- Redis Streams、`response.delta/reset/unavailable`、active response map 和模型回复流。
- Intent、Context Builder、Retriever、Plan、Replan、Approval、Tool Execution、Skill、MCP、Qdrant 和审计表。
- Temporal Continue-As-New、通用工作流平台和多 Agent。

- [ ] **Step 4：实现 Publisher 主循环**

固定协议常量：

```text
batch size       8
worker count     4
poll interval    500ms，加入 ±20% jitter
batch deadline   20s
lease            30s
Temporal timeout 5s
max backoff      5m
```

claim token 使用 Go 1.26 标准库 `crypto/rand.Text()`，并带当前实例标识。每批最多 8 条，使用 4 个固定 worker 并发处理，最多两轮 5 秒 Temporal RPC；每条结果再使用不超过 5 秒的 MySQL 更新 Context，20 秒批次期限小于 30 秒租约，因此不需要另做续租。实现使用 Go 1.26 标准库 `sync.WaitGroup.Go` 和本批 jobs channel，不引入通用协程池。

Publisher 在上一批全部结束前不认领下一批。进程关闭导致 Context 取消时，不把取消计入投递失败，也不尝试延长租约；未完成记录等待 30 秒租约自然过期后由存活实例重新认领。Publisher 对 `task.start` 和 `task.run_requested` 都调用：

```go
temporalClient.SignalWithStartWorkflow(
	ctx,
	workflow.TaskWorkflowID(taskID),
	workflow.TaskSignalName,
	workflow.TaskSignal{TaskID: taskID},
	client.StartWorkflowOptions{
		ID:        workflow.TaskWorkflowID(taskID),
		TaskQueue: workflow.TaskQueueName,
	},
	workflow.TaskWorkflowName,
	workflow.TaskWorkflowInput{TaskID: taskID},
)
```

成功和失败更新都必须带 `id + locked_by + published_at IS NULL` 条件。条件更新影响行数为 0 表示租约已经失效，旧实例直接放弃，不覆盖新认领者。即使实际调度超过 30 秒，fencing 仍保证迟到实例不能写坏新认领者状态。

Payload/MessageType 无法解码属于代码或持久化协议错误：保留 `last_error`、把下次尝试推迟 1 小时并记录告警，不删除 Outbox、不无限快速重试。

`PrepareRun(runID)` 按 Chat → Task → Run 加锁并在任何模型调用前确认当前状态，返回：

```go
type RunPreparation struct {
	Status  taskprotocol.RunStatus
	Context *NormalizationContext
}

type NormalizationContext struct {
	ChatID           uint64
	TaskID           uint64
	RunID            uint64
	TriggerMessageID uint64
	CurrentMessage   string
	PreviousInput    *TaskInput
}
```

状态语义固定为：

```text
running                    -> 读取 trigger message 和该 Task 最新 Input，返回非 nil Context
completed/failed/canceled  -> 返回已有终态和 nil Context，调用方不得再次调用模型
queued                     -> 数据不变量错误；ProcessRun 只能处理 Claim 后的 running Run
```

```text
锁 Chat → 锁 Task → 锁 Run
→ completed：读取已有结果并幂等返回
→ failed/canceled：返回已有终态
→ running：计算 next version
→ 插入 Task Input
→ Task -> waiting_for_input 或 ready
→ 插入 Assistant Message，幂等字段为 NULL
→ 插入 task.waiting_for_input 或 task.ready Event，携带 message_id
→ Run -> completed
→ TouchChat
→ COMMIT
```

- [ ] **Step 6：实现永久失败事务**

```text

→ Run 不是 running：幂等返回已有终态
→ 当前 Run -> failed
→ Task -> failed
→ 按 ID 升序锁定并取消其余 queued Run
→ 每个被取消 Run 写 run.canceled Event
→ 创建固定用户可读 Assistant Message
→ 写 run.failed Event，携带 failure_code 和 message_id
→ TouchChat
→ COMMIT
```

Service 主流程固定为：

```text
PrepareRun
→ completed/failed/canceled：直接返回已有 Status，不调用模型
→ running：Eino Normalizer
→ Catalog.Compose
→ 把规范化结果和 Assistant 文本保留在当前 Activity 内存
→ CompleteRun；仅对 MySQL 瞬态错误原地退避重试
→ 返回提交后的 Run Status 和 CommittedEvent
```

模型和 Composer 成功后，Service 不能把 `PERSISTENCE_RETRYABLE` 直接返回给 Temporal，否则下一次 Activity attempt 会再次调用模型。它使用当前 Activity Context 做一个局部完成循环：初始 1 秒、最大 30 秒指数退避并加入 ±20% jitter，只重试 `mysqlx.IsTransient`；等待使用 `time.NewTimer` 与 `ctx.Done()`，Context 取消时立即结束，不使用不可取消的 `time.Sleep`。Heartbeat ticker 继续由 Handler 维持。非瞬态数据库错误立即返回 protocol 错误。这个循环不抽成通用重试框架，不新增表，也不把 goal、constraints、missing information 或 Assistant 文本写进 Temporal Payload。

Activity Context 取消、Worker 崩溃或 30 分钟 StartToCloseTimeout 到期时，内存结果会丢失，后续 attempt 可能再次调用模型；这是当前至少一次边界。正常的短时 MySQL 故障不会每 30 秒重新花一次模型费用，也不会因为模型第二次输出不同而提交另一个结果。

Service 使用一个带 `Kind` 的 `ProcessError` 向 Handler 区分真实边界：

```text
normalization_permanent  模型两次都无法给出合法结构；允许转成用户任务失败
model_retryable          网络超时、429、5xx；Temporal 有限重试耗尽后允许转成用户任务失败
persistence_retryable    PrepareRun 阶段的 MySQL 瞬态错误；持续恢复，绝不能转成 NORMALIZATION_FAILED
dependency               模型 400/401/403、错误配置或不支持的协议；系统故障，不修改用户 Task 终态
protocol                 Payload、关联关系或数据不变量损坏；系统故障，不修改用户 Task 终态
```

Handler 用 `errors.As` 读取 `ProcessError.Kind`，映射为 Task 2 的稳定 Temporal Application Error Type；禁止靠错误字符串判断。Handler 不直接串联 Store、Normalizer、Composer 和完成事务。

- [ ] **Step 3：实现长期 Task Workflow**

```go
func (h *Handler) Workflow(ctx workflow.Context, in workflow.TaskWorkflowInput) error {
	signalCh := workflow.GetSignalChannel(ctx, workflow.TaskSignalName)
	for {
		claim := workflow.ClaimNextRunResult{}
		if err := workflow.ExecuteActivity(ctx, workflow.ClaimNextRunActivityName, workflow.ClaimNextRunInput{TaskID: in.TaskID}).Get(ctx, &claim); err != nil {
			return err
		}
		if claim.Terminal {
			return nil
		}
		if claim.Idle {
			var signal workflow.TaskSignal
			signalCh.Receive(ctx, &signal)
			if signal.TaskID != in.TaskID {
				return temporal.NewNonRetryableApplicationError("task signal mismatch", "TASK_SIGNAL_MISMATCH", nil)
			}
			continue
		}
		processFinished := false
		for !processFinished {
			result := workflow.ProcessRunResult{}
			err := workflow.ExecuteActivity(ctx, workflow.ProcessRunActivityName, workflow.ProcessRunInput{RunID: claim.RunID}).Get(ctx, &result)
			if err == nil {
				processFinished = true
				continue
			}

			switch applicationErrorType(err) {
			case workflow.ApplicationErrorTypeNormalization, workflow.ApplicationErrorTypeModelRetryable:
				if failErr := workflow.ExecuteActivity(ctx, workflow.FailRunActivityName, workflow.FailRunInput{
					RunID: claim.RunID, FailureCode: task.FailureCodeNormalization,
					FailureMessage: "任务处理失败，请稍后创建新任务重试",
				}).Get(ctx, nil); failErr != nil {
					return failErr
				}
				processFinished = true
			case workflow.ApplicationErrorTypePersistenceRetryable:
				if err := workflow.Sleep(ctx, 30*time.Second); err != nil {
					return err
				}
			default:
				return err
			}
		}
	}
}
```

实际代码避免本地 `internal/workflow` 与 Temporal `workflow` 包的别名冲突；以上代码冻结错误分流和恢复控制。`applicationErrorType` 使用 `errors.As` 解开 `temporal.ActivityError` 与 `temporal.ApplicationError`，不解析 Message。

Normalizer 永久格式失败立即进入 FailRun；可重试模型错误在一次 Activity 的三次尝试全部耗尽后进入 FailRun。模型调用前的 PrepareRun 如果遇到 MySQL 瞬态错误，会返回 `PERSISTENCE_RETRYABLE`；该类型耗尽一轮重试后，Workflow 固定等待 30 秒再开始下一轮，直到数据库恢复，期间尚未发生模型调用。模型成功后的 CompleteRun 瞬态错误由同一个 Activity 持有结果原地恢复，不回到 Workflow。两种数据库故障都不会调用 FailRun。依赖配置、非法 Payload、未知错误和数据不变量错误让 Workflow 失败并告警，由 Reconciler 保留恢复入口，不能伪装成普通用户任务失败。

Workflow 不调用 MySQL、Redis 或 Eino，不使用 `time.Now`、goroutine 或非确定性 API。

- 严格解码 `chat_id`、`event_id`，非法通知记录告警并丢弃；
- 按 chat_id 通知本实例连接；
- 每个连接的 wake channel 容量为 1，使用非阻塞发送并允许合并提醒；
- Hub 不缓存 Task Event 正文，不承担断线重放。

Hub 不建立共享 Frame 队列；它只合并 wake。Task 11 在每条 SSE Connection 内建立独立的有界 Frame 队列，因此慢客户端不会阻塞 Redis 订阅或其他连接。

- [ ] **Step 5：在事务提交后 best-effort Publish**

```text

ClaimNextRun -> run.started
CompleteRun -> task.waiting_for_input / task.ready
FailRun -> run.failed / run.canceled
```

Service 在 COMMIT 后 Publish。Publish 失败只记录 `chat_id`、`event_id`、错误分类，不返回给已经成功的 HTTP/Activity；SSE fallback poll 会补偿。

- [ ] **Step 4：建流前完成全部校验**

`GET /api/v1/chats/:chat_id/events`：

- Last-Event-ID 缺失为 0；提供时必须恰好一个无符号整数；

- Chat 不存在返回 404；

- 只有校验成功后才写 `text/event-stream` Header。

- [ ] **Step 5：实现无竞态的重放顺序**

```text
先向 Realtime Hub 注册 chat_id wake channel
→ 分页读取并写出 MySQL Event，直到当前已提交事件排空
→ 等待 Redis wake、1s fallback ticker 或 15s heartbeat
→ wake/poll 后再次分页排空
```

先订阅再重放避免“重放完成与订阅建立之间”产生低延迟通知空窗；即使 Redis 通知丢失，1 秒 poll 仍会找到 MySQL Event。

- [ ] **Step 6：正确写 SSE**

成功 Header：

```text
Content-Type: text/event-stream
Cache-Control: no-cache, no-transform
X-Accel-Buffering: no
```

不写 `Connection: keep-alive`。Frame 格式：

```text
id: 7008
event: task.waiting_for_input
data: {...}

```

data 使用 `encoding/json`，禁止字符串拼 JSON。每次写前使用 `http.NewResponseController` 设置 10 秒 Write Deadline，写完 Flush。Heartbeat 使用 `: heartbeat\n\n`，不创建数据库 Event。

- [ ] **Step 7：慢客户端和停机**

每条 SSE 连接只有一个写 goroutine。MySQL Event 和 Heartbeat 先进入该连接自己的 `frameQueue`：最多 256 个 Frame 或 1 MiB，任一超过立即取消连接；队列字节数只由这个小类型维护，不做全局共享状态。

Redis Hub 只投递容量 1 的 wake，不接触 Frame Queue。写超时、队列满或 Context 取消时立即注销订阅并结束连接；浏览器随后按 Last-Event-ID 重放。

apiserver Shutdown 取消 Hub 和现有请求 Context；当前不实现 server.reconnect、Response reset 或 Streams 重放。
